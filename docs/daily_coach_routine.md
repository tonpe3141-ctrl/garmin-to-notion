## 実行手順

### STEP 0 — 今日の日付を確定する

```bash
TZ=Asia/Tokyo date +"%Y-%m-%d (%a) %H:%M JST"
```

以降「今日」はこの JST の日付を指す。UTC の日付と混同しないこと。

### STEP 1 — 前提条件と分析手順を読む

**必ずこの順で2つとも読む。**

1. `docs/athlete_profile.md` — **前提条件の唯一の正。**
   目標レース・レース日・目標タイム・ペースゾーン・身体データ・ロードマップ・現状の課題・
   コーチングの基本姿勢が書かれている。
2. `docs/claude_project_running_instructions.md` — 分析手順。
   練習種別の判定基準と5軸評価が書かれている。
   同ファイルの「STEP 2 重複チェック」と「STEP 5 Notion への自動登録」は
   2026-09-11 に廃止したので実行しない。

**前提条件は絶対に他の場所から拾わない。** この手順書にも、トリガーのプロンプトにも、
昨日のダッシュボードにも、レース名や日付が書かれていることがあるが、
それらはすべて古い可能性がある。`athlete_profile.md` の内容だけを信じること。

矛盾が生じた場合の優先順位は `athlete_profile.md` > `claude_project_running_instructions.md` > この手順書。

### STEP 2 — データを取得する

Google Drive MCP の `read_file_content` で以下を読む。

- fileId: `1OnOX6UxztuNBqixW8g8-N8YljathVDJ26HboLNdQISU`（ドキュメント名「ランニングログ」）

読んだら先頭行の `最終更新: YYYY-MM-DD HH:MM JST` を必ず確認する。

  あわせて「データが N 日前のものです。GitHub Actions の同期が失敗している可能性があります」を
  `issues` の先頭に書く（`meta.note` は 2026-09-30 に廃止）。
  分析自体は入手できている最新データで続行し、勝手に中止しない。

### STEP 3 — 前日の状態を読む（**公開済みダッシュボードから読む**）

WebFetch で固定URLを取得する。

```
WebFetch(
  url: "https://claude.ai/code/artifact/eedcbce5-cbe3-45f2-8181-4fffcd8b79c4",
  prompt: "DATA ブロックの today.date, today.verdict, today.headline, today.points, tomorrow の全項目, week.totalKm を報告して"

```

これが**昨日の分析結果**である。特に `tomorrow`（昨日出した今日向けの指示）を確認し、
**その指示に対して実際の走りがどうだったかを、今日の評価に必ず織り込む。**
これがこの仕組みの肝で、単発の講評ではなく連続したコーチングになる部分。

> **リポジトリの `dashboard/index.html` の DATA を昨日の状態だと思わないこと。**
> 日々の DATA は publish でしか更新されないので、**昨日の DATA は常に公開済み Artifact の側にある。**
> 一方で**描画レイヤー（HTML / CSS / 描画スクリプト）の正はリポジトリの main**である（2026-09-26〜）。
> 土台の扱いは STEP 6 を見ること。
>
> なおこのWebFetchは STEP 6 の publish の前提でもある（未読のまま publish しようとすると
> 「This session hasn't viewed the latest version」で拒否される）。
> **ただし WebFetch の要約だけでは足りず、保存されたソース全文を Read するまで
> publish は通らない。** WebFetch の結果の1行目に
> 「full HTML saved to <パス>」とローカルの保存先パスが書かれているので、
> そのファイルを**最後の行まで** Read すること（1700〜2300行。数回に分けて読む）。
> このパスは STEP 6 の `splice_dashboard.js` の `--published` にも渡す（描画レイヤーの差分の報告用）。

### STEP 4 — 分析する

`docs/claude_project_running_instructions.md` の STEP 3（コーチ分析）に従う。

1. **練習種別の判定** — 平均心拍・距離・ラップ構成・トレーニング効果から判定
2. **5軸評価** — ペース管理 / 心拍コントロール / フォーム指標 / 疲労・コンディション / 総合評価
3. **総合評価** — ◎完璧 / ○合格 / △要調整 / ✕中止

守るべき姿勢:

- **過大評価しない。△の走りに○をつけない。**
- 「心拍で走る、ペースは結果」——心拍が主、ペースが従
- 週間距離は**急な跳ね上がり**（2週間で +30% 超、特に谷の週の直後）を過負荷リスクとして指摘する。
  前週比 +10% を超えたこと自体は指摘しない（根拠が弱い。プロファイル「負荷の調整」参照）
- 上下動はドライブの値を **cm としてそのまま**読む（`上下動: 8.4 cm` なら 8.4cm）。
  **×10 しないこと。** 2026-09-20 まで取得側が二重に /10 していて 8.4cm が 0.8 に
  潰れていたため「×10 して読む」という回避策を置いていたが、取得側を直したので廃止した。
  - **`上下動:` の項目が出ていない日は「取れなかった」日である。** 欠測として扱い、
    `stats` の値を `"—"`、`state` を `"warn"` にして `issues` と `health.read` に
    取れていないことを書く。**推測値で埋めない。評価軸の講評でも触れない。**
  - **小数第1位まで動いていることを必ず確認する。** 7.5〜8.5cm が全部 0.8 に
    見えていたのが今回の不具合なので、値が 0.1 刻みで動いていない週が続いたら
    取得側を疑うこと（`src/ガーミン活動データ取得.py` の `format_vertical_oscillation`）。
- 疲労・コンディション軸は**必ず健康データで裏を取る**。走行データだけで疲労を語らない。
  見る材料は次のとおり（重い順）:
  1. 朝の HRV が普段の変動幅（バランス域）を下回る
  2. 安静時心拍が平常比 +5bpm 以上で2日続く
  3. ボディバッテリー最低値が 20 未満（特に連日。前日までの確定値で見る）
  4. 睡眠スコアの週平均が 70 未満
  5. トレーニング準備度（**朝の値が他の材料と揃って低いときだけ**。単独では使わない）
  出ていた材料は「疲労・コンディション」軸の `summary` と `issues` に、具体的な数値とともに書く。
  **材料が出たときにどう処方を変えるかは、プロファイルの「負荷の調整 — 根拠にもとづく判断」で決める。**
  ここに並べたのは書く順番であって、「出たら休養」のスイッチではない。
- **当日の行（2026-09-26〜）:** 取得のタイムゾーンを JST に直したので、当日朝の睡眠・HRV・
  安静心拍・準備度が入るようになった（それまでは当日の行が毎日空だった）。
  ただし当日の**ボディバッテリー最低・ストレス・歩数は取得時点までの途中値**
  （ドキュメントの当日行に「※当日: …途中値」と出る）。朝の BB は高く出るので、
  **当日の `bbLow` / `stress` / `steps` は `null` にし、判定にも使わない。**
  「BB最低 < 20 が2日連続」などは前日までの確定値で見る。週平均はドキュメント側で当日の途中値を除いてある。
- **準備度は「朝の値」ではない（2026-09-27 追加）:** 取得するのは取得時点の最新値なので、
  **走った日は走行後に下がった値**が入る（9/27 は24kmロングの後で 26）。
  走行後の低い準備度は、その走りの負荷を映しているだけで、翌朝の状態を表していない。
  - 走った日の当日の準備度を「準備度 < 30」「< 50 が3日連続」の判定に使わない。
    書くときは「走行後の値」と明記する。
  - 準備度の週平均と前週比にも走行後の値が混ざる。**準備度の前週比だけを根拠に負荷を落とさない。**
    HRV・安静時心拍・BB最低（前日まで）のどれかが同時に出ているときだけ、サインとして数える。
  - 朝の値であっても、ロング・レースの後1〜3日は準備度が低く出るのが普通（直近の負荷と回復時間が入るため）。
- 健康データが空欄の日がある場合は、その項目を `null` にして
  「取れていない」ことを `issues` と `health.read` に明記する。
  0 や推測値で埋めない。

**今日走っていない場合**（最新のランが今日でない）:
`today.type` を `"休養日"`、`verdict` を `"—"`、`verdictLabel` を `"休養"`、`stats` と `laps` を空配列にし、
`headline` に休養の妥当性（連続走行日数・週間距離から見て適切か）を1文で書く。
`points` には休養の根拠を要点で置く（`tone` は `"note"` を基本に、
週の未達など問題があれば `"bad"`）。
評価軸と明日のメニューは通常どおり出す。休養日こそ翌日の設計が重要。

### STEP 5 — 明日のメニューを決める

`tomorrow` に、そのまま実行できる具体度で書く。抽象論を書かない。

- `title` — メニュー名（例: `Eペースロング 14km`）
- `headline` — 明日いちばん意識すべき一文（1〜2文）
- **`segments[]` — 練習の構成。ここが本体。** 各要素は
  `{ zone, km, label, pace, hr, note }`。
  - `zone` は `"E"` / `"M"` / `"T"` / `"R"` / `"rest"`（週プランと同じ区分）
  - `km` は数値。描画側が**距離の比率をそのままバーの幅**にするので、必ず入れる
  - `label` は区間名（`Eペース` / `Mペース本セット` / `クールダウン`）
  - `pace` / `hr` は帯で（`4:20〜4:30` / `≤167`）。無い区間は `"—"`
  - `note` は一行。その区間で守ること、または止める条件をひとつだけ
  - 例: `E 14km → M 5km → クールダウン 1km` なら3要素
  - 休養日は1要素だけ: `{ zone:"rest", km:0, label:"完全休養", pace:"—", hr:"—", note:"…" }`
- `prescription` — **`segments` に入らない指示だけ**を書く（歩数・記録すること・
  補強・起床時刻など）。距離やペースをここに重ねて書かない
- `why` — なぜこの内容なのかを、週間距離・疲労・フェーズから説明する（2〜3文）
- `alt` — 当日の状態による切り替え条件（配列。各1文）。**落とす条件と、伸ばす条件の両方を書く。**
  例: 「朝の HRV が域を下回ったら E 10km に替え、M は木曜へ移す」
  「M 6km を終えて HR が 162 以下・4:15〜4:25 に入っていれば 8km まで伸ばしてよい」
- ~~`next`~~ — **2026-09-30 に廃止。書かないこと。** その先の日は `weekPlan.days` に1行ずつ出ていて、
  `next` は同じ内容を文章で繰り返すだけだった（描画もしていない）

### STEP 5.5 — 明日から1週間の流れを引く

`weekPlan` に明日から7日分を書く。**要点だけ。** 詳細は `tomorrow` 側に書くので重複させない。

- `days[]` は明日を先頭に7日。各日 `d` / `dow` / `type` / `title` / `km` / `note`
  - `type` は `"E"` / `"M"` / `"T"` / `"R"` / `"rest"`（週間バーと同じ区分）
  - `title` はメニュー名だけ（例: `Eペースロング`）。長い説明を入れない
  - `km` は文字列。幅がある日は `"14〜16"`、休養日は `"0"`（描画側が「—」にする）
  - `note` は一行。守るべき心拍かペース、または落とす条件をひとつだけ
- `aim` — **その週の練習の「目的」を1〜2文で。** 何の能力を上げにいく週なのかを書く。
  経緯の説明や言い訳を書く場所ではない（`policy` は廃止した）。
  例: 「Mペースの天井を上げること。今週は閾値が1本も入らなかったので、
  9/8 の閾値走でLTへの刺激を戻し、9/11 と 9/13 で 4:25 を切る精度を取りにいく。」
- `totalKm` — 予定合計の目安（文字列。例 `"53〜55"`）

> **この先1週間は「ねらい1文 + 7日のリスト」だけで出す。**
> 集計タイルや棒グラフを足さないこと。2026-09-06 に達成度タイルと予定バーを
> 入れてみたが、情報が重複して邪魔になるという指摘を受けて外している。

`type` は正しく付けること。`"M"` / `"T"` / `"R"` が質練習で、`"E"` は数えない
（プロファイルの定義どおり）。週間バーの色分けもこれで決まる。

引くときの原則:

**まず骨格を置き、そのあとで調整する。** 空いた日をEで埋めていくのではなく、
先に質練習を配置してから残りをEと休養で埋めること。順序を逆にすると質が痩せる。

1. **フェーズ規定の質練習を先に置く**（`athlete_profile.md` のロードマップ表）。
   本数はフェーズごとに違うので、**必ず表の「質練習」欄を読んでから置くこと**
   （ビルドアップ期は週3本 — Mペース1／閾値かインターバル1／ロング（後半M混走）1）。
   この本数は出発点。動かすのは、プロファイルの「負荷の調整 — 根拠にもとづく判断」に
   照らして根拠があるときだけ（上にも下にも）。
   **曜日は固定しない。** HRV と脚の状態が良い日に質練習を寄せ、悪い日は E と入れ替える。
   > **⚠ 例外 — レース後の回復週（Phase 8・12）とレース週。**
   > 回復週は質練習ゼロ・週間距離を**上限**として扱う。テーパー週も表の本数に従う。
   > これらの週は「下限を割った」ではなく「規定どおり」なので、`issues` に書かない。
2. **質練習の間隔を空ける。** 中1〜2日。連続させない。翌日はEジョグか休養。
3. **残りをEで埋めて週間距離の帯に届かせる。** 届かないなら、
   休養日をEジョグに替えるか、Eの距離を伸ばす。**質練習を削って調整しない。**
4. **休養日は日数で決めず、その日の位置で決める**（根拠はプロファイル「負荷の調整」の「休養日」）。
   - 休む価値が高い: ロング・レース・強い質練習の翌日（24時間以内）、BB最低が続けて低い、
     体調不良、痛み、ユーザーの予定で走れない日
   - ジョグの価値が高い: 週の距離が必要、HRV は低いが痛みはない、次の質練習まで48時間以上ある
   - **HRV・安静時心拍・準備度の低下だけでは休養を足さない。** それは「低強度で走る日」である。
   - ロング翌日に走るなら HR 120台（上限130）・30〜60分。「HR ≤135 なら何kmでも」にはしない。
   - ビルド期の目安は週0〜1日。予定で走れない日は休養に数え、別に休養を足さない。
   > 2026-09-27 に、ロング直後の準備度26と HRV の域下抜けを理由に休養を2連続にしたが、
   > 根拠に照らすと「翌日（24時間以内）は休み、翌々日は軽いジョグ」か、その逆の組み方が妥当だった。
5. **週間距離は急な跳ね上がりだけを避ける。** 2週間で +30% 超、特に谷の週の直後を避ける。
   前週比 +10% は根拠が弱いので、上限として使わない。

引き終わったら、**出す前に自己チェックする:**

- 質練習はフェーズ規定の本数に届いているか（届いていないなら、その根拠を書けるか）
- 週間距離はフェーズ規定の帯に届いているか（同上）
- Mペースと、閾値またはインターバルが**両方**入っているか
- 休養日の位置が根拠に合っているか（ロング翌日を休み、HRV が低いだけの日は低強度など）
- **タイム向上に効く上方向の余地を見落としていないか**（Mペースを伸ばせる日、質練習を前倒しできる日）

> **回復週（Phase 8・12）とレース週では、上の項目をそのまま当てはめないこと。**
> これらの週は質ゼロ・低距離・休養2〜3日が規定であり、表のとおりに組めていれば合格。
> テーパーと回復を削るのは、過小負荷ではなく**シーズン設計そのものの失敗**である。

**規定から動かした場合は（上げても下げても）、その理由を
`weekPlan.aim` と `issues` の両方に必ず書く。** 理由を書けないなら、それは
動かしてよい週ではない。

### STEP 5.8 — 今日の読みものを選ぶ（2026-09-30 追加）

ランニングに関するニュース・コラム・研究を**毎日1本**選び、`news` に紹介を書く。
ホームの最後に「今日の読みもの」として出る。目的は、毎日開く理由を1つ増やすことと、
自分の練習を一段広い文脈（研究・レース・ギア）で見られるようにすること。

**1. 今日のテーマを決める（JST の曜日で固定）:**

| 曜日 | テーマ（`theme`） | 探すもの |
|------|------------------|---------|
| 月 | `研究・科学` | 持久系・マラソンの新しい研究、スポーツ科学者の解説 |
| 火 | `トレーニング` | 練習法・ワークアウト・ペース設計・コーチの解説 |
| 水 | `レース・大会` | 国内外のマラソンの結果・記録・大会ニュース（エリートと市民の両方） |
| 木 | `栄養・回復` | 補給・食事・睡眠・ケガ予防・リカバリー |
| 金 | `シューズ・ギア` | シューズ・ウォッチ・テクノロジーの新製品やレビュー |
| 土 | `コラム・人物` | ランナーの物語・インタビュー・読み物 |
| 日 | `メンタル・戦略` | レース戦略・ペース配分・メンタル・目標設定 |

曜日のテーマから外れてよいのは、**直近3日以内に大きな出来事**（世界記録・メジャー大会・日本記録・MGC 等）が
あったときだけ。その場合は `theme` を `レース・大会` にする。

**2. 重複を避ける:** STEP 3.5 の一覧から、直近に紹介した記事を出す。

```bash
node scripts/recent_news.js <スクラッチパッド>/db
```

出てきた URL は選ばない。**同じ出来事を別の媒体で書いた記事も選ばない**（例: 同じ大会の結果を2日続けない）。

**3. 探す:** `WebSearch` を2〜3回。日本語と英語の両方で探してよい。例:
`マラソン 研究 2026年10月` / `marathon training study October 2026` / `ランニングシューズ 新作 2026`

- **公開日を必ず確かめる。** 検索結果には前年の同じ大会の記事が混ざる（2026-09-30 に実際に確認した。
  「ベルリンマラソン 2026 結果」で 2025 年の結果が返ってきた）。URL・本文の日付で年を確認すること
- `kind: "ニュース"` は **14日以内**の記事だけ。`コラム` と `研究` は古くてもよいが、1年以内を優先する
- 一次情報に近いものを優先する（論文の紹介なら論文誌・大学の発表に近い媒体、大会なら公式や大手媒体）
- 選ぶ基準は「サブ3を狙う市民ランナーが、今のフェーズで読んで得をするか」。ゴシップ・広告記事は選ばない
- 記事本文は `WebFetch` で読んでよいが、失敗したら検索結果の情報だけで書く。**分からないことを推測で埋めない**

**4. 書く（`news`）:**

```js
news: {
  theme: "研究・科学",              // 上の表のテーマ
  kind: "研究",                     // ニュース / コラム / 研究
  title: "…",                       // 日本語。英語の記事は内容が分かる日本語に訳す
  source: "…",                      // 媒体名
  url: "https://…",                 // 検索結果に出た URL をそのまま。作らない・短縮しない
  published: "2026-09-28",          // 記事の公開日。日が分からなければ "2026-09"
  summary: "…",                     // 2〜3文。何が分かった／起きたのかを、数字を入れて自分の言葉で
  takeaway: "…",                    // 1文。いまの練習・フェーズ・次のレースへの引きつけ
  more: [ { title, source, url } ]  // 任意・0〜2件。今日のテーマ以外で目に留まった記事
}
```

- **記事の文章を写さない。** `summary` は自分の言葉で要約し、引用は使わない（使うとしても15字未満を1つまで）。
  `check_dashboard.js` は40字以上の「」を ✕ にする
- `takeaway` は**処方ではない。** 練習メニューを変える根拠にはしない（処方は STEP 5 がプロファイルの根拠で決める）。
  「今の Phase 5 で言えば〜」「水戸黄門では〜」のように、読んだことを自分に引きつける1文にする
- 見つからなかった日・`WebSearch` が使えない日は **`news: null`** にして先へ進む（カードが出ないだけ）。
  前日の記事を使い回さない

   - `today.headline` — その日の結論を**1文**で。ダッシュボードで最初に読まれる行。
     「何が良くて、何が外れて、総合はどうか」をこの1文に収める。
   - `today.points[]` — 要点。**4〜7個**。各要素は `{ tone, label, text }`。
     - `tone` は `"good"`（○ 良かった点）/ `"bad"`（△ 外した点）/ `"note"`（・ 留保・保留）
     - `label` は **6〜12字の名詞句**（例 `M区間 5km` / `距離 −1.89km` / `E区間の心拍`）。文にしない
     - `text` は **1〜2文**。数字を必ず入れる。3文以上書きたくなったら、要点の切り方が悪い
   - `axes[].summary` — その軸の講評を **1〜2文**で。これが軸の全文。今日の走りの細部は `points` にあるので、
     ここは「その軸で今どういう状態か」の判定と根拠の数字だけにする。

   > **⚠ 廃止したキー。書かないこと:**
   > - 2026-09-06: `today.verdictReason` と `axes[].text`（どちらも長文用）、`weekPlan.policy`、`alerts`
   > - 2026-09-30: `tomorrow.next`（`weekPlan` と重複）、`meta.note`（表示されない）、
   >   `health.baseline.hrvStatus`（表示されない。HRV の読みは `health.read` に書く）
   >
   > 昨日の公開版にこれらのキーが残っていても写さないこと（`check_dashboard.js` が ⚠ を出す）。
   > 描画側に対応するコードはもう無いので、書いても表示されない。
   > 長文は「畳めば置いておける」ものではなく、**毎日それを生成すること自体がコスト**である。
   > 要点に入らない話は、書かないという判断をすること。
   - `tomorrow.alt` — **配列**にする。1条件＝1要素で「条件 → 対応」の形。
     `①②③` の番号は書かない（描画側が振る）。

3. Artifact ツールで publish する。**必ず `url` を渡すこと。渡さないと別のURLが発行され、固定URLが壊れる。**

```
Artifact(
  file_path: "dashboard/index.html",
  url: "https://claude.ai/code/artifact/eedcbce5-cbe3-45f2-8181-4fffcd8b79c4",
  favicon: "🏃",
  title: "サブ3デイリーコーチ"
)
```

`favicon` と `title` は**毎回同じものを使う**。変えるとユーザーがタブを見失う。

### STEP 6.5 — 文章の書き方（分量の規約）

**2026-09-06 の指摘:** 講評がだらだら長く読みづらい。折りたたみに逃がすのも無駄。
**2026-09-30 の再構築:** 同じ事実（例: 「BB最低が2日連続で20割れ」）が `meta.note`・`axes`・`issues`・
`tomorrow.why`・`weekPlan.aim`・`health.summary[].note`・`health.read` の7か所に書かれ、画面でも7回読まされていた。
**書かなかったものは存在しない。書いたものは必ず読まれる。** 各フィールドの分量と置き場所は次のとおり。

| フィールド | 分量 |
|-----------|------|
| `today.headline` | 1文 |
| `today.points[].text` | 1〜2文 × 4〜7項目 |
| `axes[].summary` | **1〜2文** |
| `good[]` / `issues[]` | **各1文・それぞれ最大3項目**（優先度の高いものだけ残す） |
| `tomorrow.headline` | 1〜2文 |
| `tomorrow.why` | 2〜3文 |
| `tomorrow.alt[]` | 各1文（配列。番号は描画側が振る） |
| `tomorrow.segments[].note` | 各1行 |
| `weekPlan.aim` | 1〜2文（その週の目的） |
| `health.read` | **2〜3文** |
| `health.summary[].note` | **30字以内の1句** |
| `news.summary` / `news.takeaway` | 2〜3文 / 1文 |
| `stats[].note` / `weekPlan.days[].note` | 各1行 |

**規約1 — 結論から書く。**
「〜から書きます」「まず〜を見ます」「週の数字を置きます」といった前置きは書かない。

**規約2 — 数字を落とさない。**
短くする方法は、前置きと言い換えと繰り返しを削ることであって、根拠の数字を削ることではない。
`points[].text` には必ず具体的な数値を入れる。

**規約3 — 1つの事実は1か所だけに書く。** 置き場所は次の表で決める。
ほかのフィールドから触れる必要があるときは、数字を繰り返さず「疲労のサインがあるので」のように名前だけで指す。

| 書くこと | 置き場所（ここだけ） |
|---------|-------------------|
| 今日の走りの良かった点・外した点・数字 | `today.points` |
| 各軸の「今どういう状態か」の判定 | `axes[].summary` |
| 週・月・レースまでの残りといった一段広い視点 | `good` / `issues` |
| 疲労・回復のサインの数値（HRV・安静心拍・BB・睡眠） | `health.read`（軸 `疲労・コンディション` には判定だけ） |
| 同期の失敗・データの欠測 | `issues` の先頭（ページ上部の帯は描画側が `sourceFresh` から出す） |
| 明日のメニューをそう組んだ理由 | `tomorrow.why` |
| 週の組み方を規定から動かした理由 | `weekPlan.aim`（`issues` には「動かした」事実だけを1文） |

**規約4 — 短くすることと評価を甘くすることは別。**
`headline` に良い面だけ並べて総合評価を書かないのは違反。
外した点は必ず `tone: "bad"` で立てる。過大評価しないという原則は分量と無関係。

**規約5 — モチベーションは事実で上げる。**
褒め言葉や励ましの定型文は書かない。前進した数字（「9/20 の同じ8kmから5秒/km 速い」）を `good` と
`points`（`tone: "good"`）に立てることが、いちばん効く励ましになる。記録上の最長・フル予測の推移は描画側が出す。

### STEP 6.6 — 履歴を1件書き込む

publish のあと、**その日の評価を Artifact の db に1件だけ書く。**
ダッシュボードの「成長の記録」タブ（カレンダー・推移）はここを読んでいて、数値タイルもラップグラフも
この1件から描いている。

**中身を書き起こしてはいけない。** 必要な値はすべて publish 済みの
`dashboard/index.html` の `DATA.today` に入っているので、スクリプトに写させる。

```bash
node scripts/export_run_history.js dashboard/index.html <書き出し先>/run.json
```

> **⚠ 書き出し先に `/tmp` を使ってはいけない（2026-09-14 に判明）。**
> `Artifact` の `file_path` は **作業ディレクトリ配下か、そのセッションのスクラッチパッド配下**しか
> 黙って読めない。`/tmp/run.json` のようにその外を指すと、書き込み自体は許可されていても
> **ファイルを読むところで承認を求められ**、無人の Routine はそこで `Denied by user` になる。
> 2026-09-14 の実行で実際に2回失敗し、スクラッチパッドに置き直したら一度で通った。
>
> 書き出し先は次のどちらかにすること:
> 1. **そのセッションのスクラッチパッドディレクトリ**（環境プロンプトの `Scratchpad directory:`
>    に毎回そのセッションのパスが書かれている。セッションごとに変わるのでここに書き写さない）
> 2. それが分からなければ **作業ディレクトリ直下の `run.json`**。
>    その場合は STEP 7 で `rm -f run.json` して消すこと（消さないと Stop フックが発火する）

出力された JSON を、そのままファイル渡しで書き込む。**db を扱うツールは環境によって名前が違う**ので、
使えるほうを使う（同じ引数名。`ArtifactData` が ToolSearch に出るならそちら）:

```
ArtifactData(                       ← 2026-09-15 以降の形
  action: "set",
  url: "https://claude.ai/code/artifact/eedcbce5-cbe3-45f2-8181-4fffcd8b79c4",
  collection: "runs",
  doc_id: "YYYY-MM-DD",             ← STEP 0 で確定した今日の日付
  file_path: "<書き出し先>/run.json"
)

Artifact(                           ← 以前の形。Artifact に write_db があるときはこちら
  action: "write_db", db_op: "set",
  url: "…", collection: "runs", doc_id: "YYYY-MM-DD", file_path: "<書き出し先>/run.json"
)
```

同じ日に2本以上走った日は `export_run_history.js` が `run-2.json`, `run-3.json` … も書き出し、
最後に `doc_id -> ファイル` の一覧を出す。その全部を `action: "batch"` の `writes` に
`{ op: "set", collection: "runs", doc_id, file_path }` として並べて1回で書く。

> **⚠ この書き込みは承認プロンプトを出さない（2026-09-11 に対処、2026-09-15 に更新）。**
> db への書き込みだけが独自に承認を要求する。`publish` は `permissions.allow: ["Artifact"]` で
> 素通りするため、「ダッシュボードは更新されているのに、そのあとで承認を求められる」という形になっていた。
> 2026-09-11 の実行では実際にここで **2時間21分**（03:03 → 05:25 UTC）止まっている。
> 無人で動く Routine なので、止まれば STEP 6.6 以降が丸ごと終わらない。
>
> 対処は `.claude/settings.json` の `PreToolUse` フック（matcher は `Artifact|ArtifactData`）。
> **`runs` コレクションへの読み書き（`write_db` / `get` / `list` / `query` / `set` / `update` /
> `str_replace` / 全件が `runs` への `set`・`update` の `batch`）のときだけ** `permissionDecision: "allow"` を返し、
> それ以外には何も出力しない（＝通常どおり承認を求める）。
> したがって、別のコレクションへ書こうとした場合や `delete` は今までどおり止まる。
>
> このファイルはコンテナが破棄されても残るよう **リポジトリにコミットしてある**
> （`.gitignore` の `.claude/` に `!.claude/settings.json` の例外を入れてある）。
> 消すと承認待ちが復活するので、消さないこと。
>
> **ただしこのフックが面倒を見るのは「db に書く権限」だけで、`file_path` のファイルを
> 読む権限は別枠である。** 上の「書き出し先に `/tmp` を使ってはいけない」はそちらの話で、
> フックを直しても解決しない。書き出し先のほうを直すこと。

- `doc_id` は日付そのもの。したがって同じ日に何度実行しても行が増えることはない。
  ただし **`if_version` なしの `set` は、その日の記録が既にあると
  `version_mismatch` で拒否される**（2026-09-14 に確認。「上書きになるだけ」ではない）。
  同じ日に2回目を書くときは、先に読んでからそのバージョンを指定して書き直すこと:

  ```
  ArtifactData(action: "get", …, collection: "runs", doc_id: "YYYY-MM-DD")
  ArtifactData(action: "set", …, collection: "runs", doc_id: "YYYY-MM-DD",
               file_path: "<書き出し先>/run.json", if_version: <get が返した version>)
  ```
  （`Artifact` 形なら `action: "read_db", db_op: "get"` と `action: "write_db", db_op: "set"`）

  初回（その日の記録がまだ無いとき）は `if_version` を付けないこと。
- `file_path` を使うこと。**中身を会話に流さないのが要点で、これで履歴1件あたりの
  生成コストがほぼゼロになる。** インラインの `data:` に貼り直すと台無しになる。
- 休養日も書く。`DATA.today` を規定どおり（`type` は `"休養日"`、`verdict` は `"—"`、
  `stats` と `laps` は空配列）に作ってあれば、スクリプトがそのまま写す。
- スクリプトが `DATA ブロックが見つかりません` で失敗する場合は、STEP 6 の差し替えで
  ファイルを壊している。`splice_dashboard.js` を使っていればここで落ちることはない。

書き出される中身（すべて `DATA.today` からの機械的なコピー）:

| キー | 中身 |
|------|------|
| `d` / `dow` / `type` / `verdict` / `verdictLabel` | 一覧行に出す |
| `km` / `pace` / `hr` | `stats[]` の「距離」「平均ペース」「平均心拍」から自動取得 |
| `headline` / `points` | 開いたときの結論と要点 |
| `stats` / `effect` | 数値タイルとトレーニング効果 |
| `laps` | `"秒:心拍,秒:心拍,…"` の1行に圧縮（ペースは秒から復元するので持たない） |
| `pred` / `vo2` | その日の Garmin フル予測と VO2max（`health.fitness` から。1本目だけ。2026-09-26 追加）。「成長の記録」タブの推移とホームの「現在地」に使う |
| `news` | その日の読みもの（`DATA.news` を短いキー `t` / `u` / `s` / `th` / `k` / `p` で。1本目だけ。2026-09-30 追加）。「読みものの記録」と STEP 5.8 の重複照合に使う |

> **なぜ DATA に持たせないか。**
> 過去分を `DATA` に積むと、Routine は毎日その全部を書き直すことになり、
> 生成コストが日を追って増え続ける。db に1日1件書く方式なら、
> **DATA の大きさも1日あたりのコストも何日経っても変わらない。**
> ページ側が開いたときに直近60日を読む。
>
> db は1アーティファクトあたり5,000件まで。1日1件なので当面問題にならないが、
> 数年後に上限が近づいたら古い日を削ること。

### STEP 6.7 — 履歴の取りこぼしを埋める（2026-09-15 追加）

**この Routine は「今日の走り」しか評価しないので、次の走りは履歴に残らない:**

- 12:00 の実行までにドライブへ同期されなかった走り（8:30 の同期が遅れた、走り終わりが遅かった）
- Routine 自体が失敗した日（承認待ちで止まった、`/tmp` の読み取りで落ちた）
- 同じ日の2本目以降

2026-09-13（日）の 22.14km ロングと 9/9 の2本目がまさにこれで、翌日の分析文には出てくるのに
履歴（当時の「過去の評価」）には無い、という状態になっていた。**毎日この STEP で直近の穴を埋める。**

1. 履歴の一覧は STEP 3.5 で `<スクラッチパッド>/db` に保存してある（2026-09-30 に前倒し）。
   STEP 3.5 が失敗していたら、ここで同じ呼び出しをもう一度試す。
2. **直近14日**（今日を除く）について、ドライブの「直近4週のランニング詳細」と突き合わせる:
   - ドライブに走りがあるのに db に `<日付>` が無い、または db の `<日付>` が `休養日` → **その日を評価して書く**
   - ドライブに同じ日の走りが N 本あるのに db に `<日付>-2` … `<日付>-N` が無い → **2本目以降を書く**
   - ドライブに走りが無く db にも無い → 休養日として書く（一覧が途切れないようにするため）
   - 一致していればその日は何もしない
3. 埋める日ごとに、`DATA.today` と同じ形の JSON を `<スクラッチパッド>/entry_<日付>.json` に書く
   （`date` / `dow` / `type` / `verdict` / `verdictLabel` / `headline` / `points` / `stats` / `effect` / `laps`。
   2本目以降は `extra: [ … ]` に同じ形で。`plan` は昨日のダッシュボードから分かるときだけ）。
   **評価の基準は今日と同じ。** 後追いだからといって甘くしない。ただし分量は
   `headline` 1文 + `points` 3〜5個で足りる。`points` の最後に
   `{ tone: "note", label: "後追い記録", text: "この日の Routine は履歴を書けておらず、M/D に後追いで記録した。" }` を置く。
4. 書き出して、まとめて1回で書く:
   ```bash
   node scripts/export_run_history.js <スクラッチパッド>/entry_YYYY-MM-DD.json <スクラッチパッド>/hist_YYYY-MM-DD.json
   ```
   ```
   ArtifactData(action: "batch", url: "…", writes: [
     { op: "set", collection: "runs", doc_id: "YYYY-MM-DD",   file_path: "<スクラッチパッド>/hist_YYYY-MM-DD.json" },
     { op: "set", collection: "runs", doc_id: "YYYY-MM-DD-2", file_path: "<スクラッチパッド>/hist_YYYY-MM-DD-2.json" },
     …
   ])
   ```
   既にある `<日付>`（休養日で書いてしまった日）を上書きするときは、1. の一覧に出た
   `version` を `if_version` に付ける。

穴が無い日はこの STEP は 1. の一覧を取るだけで終わる（数秒）。
**穴があったのに埋めなかった場合は、最後の報告にその日付と理由を書くこと。**

### STEP 6.8 — iPhone ウィジェット用データを更新する（2026-09-25 追加）

iPhone のウィジェット（`widget/running_widget.js`、Scriptable）は Artifact を読めない
（claude.ai のログインが要るため）。代わりに Notion の専用ページにある JSON を Notion API で読んでいる。
そのページを、publish 済みの DATA から毎日書き換える。

- ページID: `3e5862c3-def7-815c-a6da-c05c5b756c20`（「📱 ウィジェット用データ」、親は「各種連携」）

**中身を書き起こしてはいけない。** STEP 6.6 と同じく、スクリプトに作らせる:

```bash
node scripts/export_widget_data.js dashboard/index.html <スクラッチパッド>/widget.md --history <スクラッチパッド>/db
```

- `--history` には STEP 3.5 で `out_dir` に保存した db 一覧のディレクトリを渡す。
  今日が休養日のとき、ウィジェットの「直近」に出すランをそこから拾う。
- 出力の `widget.md` は「説明1行 + JSON のコードブロック1つ」になっている。
  **その全文を一字も変えずに** `new_str` に渡す:

```
notion-update-page(
  page_id: "3e5862c3-def7-815c-a6da-c05c5b756c20",
  command: "replace_content",
  new_str: <widget.md の全文>
)
```

- ページの読み取り（`notion-fetch`）はしない。確認のために読み直す必要もない。

- **このツールが拒否されたら、そこで止まらず STEP 7 へ進む。** ウィジェットは古いデータのまま
  ⚠ を出し、受け取り済みの1週間の予定から今日のメニューを表示し続ける。
  拒否された場合は STEP 8 の通知の末尾に「（ウィジェット未更新）」と付ける。

### STEP 7 — 作業ツリーを戻す（日々の DATA はコミットしない）

**2026-09-06 に GitHub 連携が復旧し、push できるようになった。**
それでも**毎日の DATA はコミットしない。** 中身は Artifact（固定URL・版履歴あり）と
db に残っており、リポジトリに毎日 DATA の差分を積んでも履歴が汚れるだけである。
翌日の継続性は STEP 3 の公開版取得が担保する。

**publish と STEP 6.6 の履歴書き込みが両方終わったら、作業ツリーを元に戻す。**
（STEP 6.6 より先に戻すと、履歴の書き出し元が古い中身になってしまう。）

```bash
git checkout -- dashboard/index.html
git status --porcelain   # 何も出なければOK
```

この環境には「未コミットの変更が残っていたらコミットして push しろ」と要求する
Stop フックが仕込まれている。上のコマンドで作業ツリーを綺麗にしておけば、
フックは発火せず、無駄なやり取りが起きない。

**例外 — コミットしてよいもの:** 描画レイヤー（HTML / CSS / 描画スクリプト）の修正、
この手順書、`docs/athlete_profile.md`、`scripts/` 配下。
これらは「その日のデータ」ではなく仕組みそのものなので、直したならコミットして push する。
その場合は `main` に直接ではなくブランチを切ること。

### STEP 8 — 通知する

`PushNotification` で、総合評価と明日のメニュー名を1行で送る。

例: `8/21 Eペース走 ○合格 ／ 明日: Eペースロング 14km（HR140厳守）`

`news` が `null` の日は末尾に「（読みもの未取得）」を付ける。`WebSearch` が許可ツールに無くて呼べなかった
場合は、最後の報告にもその旨を書く（ユーザーが Routine の設定に `WebSearch` を足せば直る）。

## この Routine が使うスクリプト（`scripts/`）

| スクリプト | 役割 | 使う STEP |
|-----------|------|----------|
| `splice_dashboard.js <data_block.js> [out] [--published <公開済み.html>]` | リポジトリの描画レイヤーに DATA とプロファイル由来の `season` を差し込み、検証してから書く | 6 |
| `profile_season.js [profile.md]` | プロファイルの表からフェーズ・レース・Mペース量の目標を読む（splice が使う。単体で実行すると JSON を表示） | 6 |
| `check_dashboard.js <html> [--render] [--shot out.png]` | 骨格と DATA の検証。`--render` で Chromium 描画、`--shot` で PNG | 6（publish 直前） |
| `export_run_history.js <html または entry.json> <run.json>` | `DATA.today`（または同じ形の JSON）から履歴を書き出す。`extra[]` があれば `run-2.json` … も | 6.6 / 6.7 |
| `export_widget_data.js <html> <out.md> [--history <dir>]` | DATA から iPhone ウィジェット用の JSON を作り、Notion ページの本文の形で書き出す | 6.8 |
| `recent_news.js <db_dir> [--days 45]` | 直近に紹介した読みものを一覧する（同じ記事・同じ話題を選ばないため） | 5.8 |

描画側で決め打ちにしている値（`dashboard/index.html` の `ZONE_EDGE` / `HR_CAPS` / `M_EDGE` / `E_BAND`）は
`docs/athlete_profile.md` のペースゾーンから引いている。**プロファイルのゾーンを引き直したら
ここも一緒に直す**（ラップの色分けと心拍上限線に使う）。

## 失敗したときの扱い

- **どのステップで失敗しても、そこで止まらず残りを実行する。**
- Google ドライブが読めなかった場合のみ、ダッシュボード更新を諦めてよい。
  その場合は `PushNotification` で「ドライブが読めず分析できませんでした」と通知する。
- **承認を求めてくるツールは呼ばないこと。** 無人で動く Routine は承認待ちで止まり、
  その先のステップが丸ごと終わらない。2026-09-11 の Notion 登録がその例で、廃止した。
  STEP 6.8 の Notion 更新はフックで allow / deny が即決するので、承認待ちにはならない。
